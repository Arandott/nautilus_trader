# 第三章 系统需求分析与总体设计

## 3.1 系统需求分析

在前两章完成问题界定和技术铺垫之后，本文需要进一步回答一个更直接的问题：面向低延迟交易场景的本地 L2 订单簿维护系统，究竟应当具备哪些能力，以及这些能力应当如何被组织。由于本文的研究对象并不是抽象的数据结构习题，而是围绕原始 L2 增量 `delta` 展开的本地维护系统，因此第三章的需求分析既要覆盖订单簿状态维护本身，也要覆盖后续实验验证、结构切换和结果复现所必需的系统能力。

### 3.1.1 功能需求

首先，系统需要具备统一的数据输入与顺序处理能力。本文的外部输入来自交易所原始 L2 增量数据集，经解析后形成连续的 `OrderBookDelta` 或 `OrderBookDeltas` 序列。由于本地簿面状态依赖前序状态逐步演化，系统必须严格按照输入顺序应用增量，不能在处理中打乱事件次序，也不能在不同实现之间引入不一致的输入适配逻辑。换言之，同一份原始 `delta` 流必须能够在 baseline 与所有特化结构之间共享，这是整个系统得以成立的前提。

其次，系统需要具备统一的订单簿状态维护能力。无论底层采用原生 `OrderBook(BookType::L2_MBP)`，还是采用 `L2TreeBook`、`L2VecBook` 或 `L2GridBook`，系统都应能够围绕同一语义完成价位新增、数量更新、价位删除以及簿面清空等基本操作，并在处理过程中维护 sequence、时间戳和更新计数等状态信息。对论文而言，这一能力对应的是“在同一问题语义下支持多种结构实现”，而不是分别构建多个互不兼容的实验程序。

再次，系统需要提供统一的核心查询能力。低延迟交易和策略研究最常使用的盘口信息包括 best bid、best ask 以及前若干档 price level，因此系统至少需要支持最优价、最优量和 top-N 深度查询。只有在这一层接口保持统一，baseline 与特化结构之间的性能与正确性比较才具备可解释性。与此同时，查询接口还应尽量与订单簿内部表示解耦，使上层调用方无需感知底层究竟是树结构、向量结构还是 grid 结构。

此外，系统还需要具备验证与测量支撑能力。本文并不满足于“结构已经实现”，而是要求不同实现能够在统一条件下完成正确性验证与性能测量。因此，系统需要支持 replay-only 与 replay+query 两类工作负载，需要支持 microbench 与真实回放两种入口，也需要支持结果记录、指标输出和后处理汇总。更具体地说，系统应能够在相同输入、相同查询深度和相同运行模式下切换不同订单簿实现，并输出可供后续统计与论文分析使用的结构化结果。

最后，系统需要具备研究闭环能力。本文的工作并不止于一次性演示，而是希望形成一个可重复、可扩展、可继续调优的本地 L2 维护原型。因此，系统既要支持小规模调试，也要支持全量 replay；既要支持 correctness 抽样检查，也要支持实验结果归档与汇总。只有在这些能力同时具备的情况下，论文中对不同设计路线的比较才不只是静态描述，而是建立在真实系统闭环之上的工程分析。

### 3.1.2 非功能需求

从非功能角度看，低时延与高吞吐是系统最核心的性能要求。本文研究的问题边界决定了系统必须能够在连续到达的 L2 增量输入下完成快速更新，并在有查询需求时尽量减少额外开销。这里的“低时延”并不只体现在单次查询上，也体现在增量维护路径的压缩、热点路径的简化以及避免不必要的结构跳转上；“高吞吐”则要求系统能够在长时间回放过程中持续处理大规模 `delta` 流，而不会因内部组织方式不当导致整体处理速率明显下降。

与性能要求同等重要的是正确性可验证。订单簿维护系统的价值首先来自状态可信，而不是指标好看。若某一实现无法在相同输入下复现与 baseline 一致的最优价、top-N 深度和最终状态，即使局部跑分更优，也无法为交易和研究提供可靠基础。因此，正确性要求不仅是测试环节的附加项，而是系统设计阶段就必须嵌入的基本约束。

内存占用可控也是本系统的重要非功能需求。本地订单簿维护往往需要面对高频增量流和较长持续时间的回放过程，若数据结构在状态表达上引入过高的额外成本，就会影响缓存行为、运行稳定性和后续扩展空间。正因为如此，本文在结构设计中不仅关心更新和查询，还显式关注不同实现的内存占用表现。

除此之外，系统还需要满足可扩展、可复现和低侵入性要求。可扩展意味着系统不应把某一种结构路线写死，而应允许在统一接口下继续加入新的 L2 特化实现；可复现意味着相同数据、相同参数和相同代码版本下的实验结果应当能够被重新获得；低侵入性则意味着本文的研究实现应尽量建立在现有仓库和既有抽象之上，避免对主仓库已有订单簿语义造成不必要的破坏。上述非功能需求共同决定了第三章后续总体设计的组织方式。

## 3.2 系统总体设计

基于上述需求，本文将本地 L2 订单簿维护系统设计为一个围绕统一输入、统一抽象和统一验证闭环展开的分层系统。系统总体思路是：以原始数据集为输入，以解析后的 `delta` 流为中间语义，以 `L2BookOps` 作为内部抽象边界，在该抽象之下接入 baseline 与三种特化结构，并通过查询、验证和测量模块形成完整的实验闭环。该设计的重点不在于把所有功能都压入同一个程序，而在于保证系统中不同部分围绕同一组语义协同工作。

需要明确指出的是，本文系统并非脱离既有框架从零构建，而是基于 `NautilusTrader` 开源量化交易框架开展扩展设计与实现。具体而言，本文沿用了 `NautilusTrader` 已有的数据模型、原生 `OrderBook(BookType::L2_MBP)`、相关 crate 组织方式以及 benchmark 与 replay 所依赖的运行环境，并在这一基础上围绕本地 L2 订单簿维护问题引入统一 `L2BookOps` 抽象、三种特化结构实现以及相应的验证与测量链路。这样的系统起点一方面保证了 baseline 的真实工程代表性，另一方面也使本文的改进工作能够直接建立在现有生产代码与实验框架之上。

图 3-1 建议放在本节开头附近。图中可按从左到右的方式表示系统主链路：原始 L2 数据集输入，经解析模块转化为统一的 `OrderBookDelta` 流；随后，由 replay runner 或 benchmark harness 通过 `L2BookOps` 接口驱动 baseline、`L2TreeBook`、`L2VecBook` 与 `L2GridBook` 中的某一种具体实现；订单簿状态在持续更新的同时，对外提供 best bid/ask 与 top-N 查询结果，并接受 correctness 检查与性能测量；最后，运行结果被写出为结构化指标，再由结果汇总脚本进行统计整理，服务于第五章的实验分析。

从层次上看，系统可以划分为五个相互衔接的部分。第一层是数据输入与解析层，其职责是读取原始 L2 数据集，并保持输入顺序与精度信息的一致性。第二层是统一订单簿抽象层，其核心是 `L2BookOps` 接口，用于为 baseline 与不同特化结构提供同构的创建、更新、查询和重置能力。第三层是具体实现层，包括原生 `OrderBook(BookType::L2_MBP)` 以及 `L2TreeBook`、`L2VecBook`、`L2GridBook` 三种 L2 特化结构，它们分别代表通用基线和三条不同的专门化路线。第四层是验证与测量层，负责驱动 replay-only、replay+query 以及 microbench 等不同工作模式，并采集吞吐、查询耗时、更新计数和内存等指标。第五层是结果整理与分析层，负责将原始输出转化为可比较的结果表、摘要文件和后续论文材料。

这一总体设计有两个关键特点。其一，原始 `delta` 始终被视为系统的统一输入与 `source of truth`。也就是说，系统中的任何实现都不能自行改变输入语义，也不能使用不同的数据适配路径来获取“额外优势”。其二，`L2BookOps` 被设计为系统内部的核心边界。统一接口的意义在于，使 replay runner 和 benchmark harness 在不知道底层具体结构的情况下，也能以一致方式调用不同实现，从而把“实现差异”尽量限制在订单簿内部，而把“实验条件差异”降到最低。

进一步看，该架构并不把 baseline 与特化结构割裂开来，而是明确把 baseline 视为系统中的组成部分。一方面，baseline 是 correctness 的参考实现与性能对照对象；另一方面，它也是统一接口和统一工作负载是否成立的重要检验对象。只有当 baseline 能够和三种特化结构共同置于同一运行闭环中时，本文才能把“结构优化”解释为“在相同系统任务下的不同工程实现”，而不是把不同程序的局部跑分简单拼接成对比。

因此，第三章的总体设计并不是单纯给出一个程序框图，而是明确回答了后续实现章节需要解决的三个问题：系统如何共享同一输入语义，如何在同一抽象边界下容纳多种结构实现，以及如何把正确性、性能与结果汇总组织成同一研究闭环。第四章的具体实现，正是在这一总体框架下展开的。

## 3.3 功能模块设计

### 3.3.1 数据输入与解析模块

数据输入与解析模块位于系统最前端，其职责是从原始数据集中读取交易所 L2 增量数据，并将其转化为系统内部统一使用的 `OrderBookDelta` 流或批量 `OrderBookDeltas`。该模块不仅负责“把文件读进来”，更重要的是保证不同实现共享完全一致的输入序列、精度设定和事件顺序。对于本系统而言，这一模块是所有后续比较成立的基础，因为一旦不同实现接收到的输入在解析阶段就发生偏移，则后续 correctness 与性能结论都将失去意义。

从与其他模块的关系看，数据输入与解析模块向下游提供的是与实现无关的统一增量语义，而不是针对某一种订单簿结构定制的数据格式。这样设计的好处在于，系统在替换底层订单簿实现时，不需要同步改动数据入口，也便于 replay runner、correctness harness 和 microbench 工具围绕同一输入前提组织工作。

### 3.3.2 订单簿核心维护模块

订单簿核心维护模块是整个系统的中心模块。它以 `L2BookOps` 为统一抽象，对外暴露创建、更新、批量应用、重置、最优价访问和 top-N 查询等核心能力，对内则屏蔽 baseline 与不同特化结构的实现差异。在这一模块下，原生 `OrderBook(BookType::L2_MBP)` 作为 baseline 被纳入统一接口，而 `L2TreeBook`、`L2VecBook`、`L2GridBook` 则作为三条不同的专门化实现接入同一调用框架。

该模块的主要职责有三点。第一，围绕统一语义执行增量更新，使系统能够在相同 `delta` 输入下驱动不同实现。第二，对上层提供一致的查询接口，使 replay runner、benchmark harness 和 correctness 检查无需感知底层结构细节。第三，为第四章的实现组织奠定边界，即把“哪些逻辑属于统一系统能力”和“哪些逻辑属于具体结构实现”区分开来。通过这一模块，本文能够把研究重点集中在 L2 维护路径本身，而不是把大量比较工作耗散在接口兼容和调用方式差异上。

### 3.3.3 查询与校验模块

查询与校验模块直接面向系统的可信性需求。一方面，该模块负责在 replay 过程中按统一方式执行 best bid/ask 和 top-N 查询，为后续特征提取与性能评估提供基础。另一方面，该模块承担 correctness 检查职责，将 baseline 与候选实现的对外状态统一转换为可比较的 price-size 序列，用于抽样检查点比较、最终状态比较以及必要时的指定价位比较。

该模块与订单簿核心维护模块紧密相连，但又不应直接依赖某一种内部结构表示。这样做的目的是避免把 correctness 检查写成“检查内部字段是否相同”，而是回到订单簿对外应有的状态语义上。对于本论文而言，这一模块的存在意味着性能优化始终受到正确性约束，也意味着第五章中的所有性能比较都建立在先通过 correctness 检查的前提之上。

### 3.3.4 Benchmark 与 Replay 运行模块

为了同时覆盖原子路径分析与真实工作负载分析，本文将 Benchmark 与 Replay 运行模块分为两类入口。第一类入口是 microbench，对已热身的订单簿执行更新已有价位、插入新价位、删除已有价位、best bid/ask 查询和 top-N 查询等局部操作，以观察不同结构在细粒度路径上的差异。第二类入口是真实 replay runner，它围绕统一数据集执行 parse-only、replay-only 和 replay+periodic-query 等模式，用于测量整体吞吐、查询额外开销和内存占用。

这两个入口虽然关注点不同，但都围绕统一抽象和统一实现集合展开。也就是说，不论是 microbench 还是 replay，系统都通过同一组 book 类型标签与统一接口切换 baseline、`L2TreeBook`、`L2VecBook` 和 `L2GridBook`。这种设计使局部路径分析与整体工作负载分析能够在同一实验框架下相互印证，避免出现“局部测量口径”和“整体测量口径”彼此割裂的问题。

### 3.3.5 结果采集与汇总模块

结果采集与汇总模块位于系统运行链路的末端，其职责是将 replay runner 与 benchmark 的原始输出统一整理为结构化结果文件，并进一步生成汇总结果与摘要材料。具体而言，该模块记录的数据包括总耗时、updates/s、查询次数、平均查询耗时、峰值内存等关键指标，并在多次重复实验后完成统计与归档。对论文写作而言，这一模块的价值在于把“单次程序运行的控制台输出”转化为“可追踪、可比较、可复用的实验材料”。

该模块同时也是研究闭环的重要一环。若没有结果汇总模块，系统虽然能运行，但很难支撑多轮实验之间的横向比较，也不利于后续章节对不同设计路线进行系统分析。因此，本模块虽然不直接参与订单簿状态更新，却是整个系统从工程实现走向可验证研究结论的必要支撑。

## 3.4 系统设计优劣分析

从整体设计看，本文系统的首要优点在于采用了统一输入、统一接口和统一验证闭环的组织方式。通过把原始 `delta` 流固定为共同输入，并以 `L2BookOps` 作为抽象边界，baseline 与三种特化结构能够在相同语义和相近调用方式下被驱动。这种设计显著降低了“因为实验框架不同而导致结果不可比”的风险，使第五章中的性能差异更容易被解释为结构与实现上的差异，而不是外围流程差异。

第二个优点在于系统保留了 baseline 的核心地位。本文并没有绕开原生 `OrderBook(BookType::L2_MBP)` 重新构造一个脱离现有仓库的实验环境，而是把 baseline 明确纳入同一框架，既将其作为正确性参考实现，也将其作为通用语义代表实现。这样做的好处是，论文中的优化路线始终建立在真实工程起点之上，而不是建立在人为削弱的“伪 baseline”之上。

第三个优点在于系统把 correctness 与性能测量放在了同一设计链路中。很多结构优化工作容易只强调吞吐和查询耗时，而忽略状态一致性和回放语义；本文系统则在总体设计阶段就把正确性检查、microbench、真实 replay 与结果汇总并列考虑，使“先证明结果没有变，再比较性能”成为系统内置原则。这种设计提高了实验结论的可信度，也有助于在后续调优过程中更快定位问题来源。

第四个优点在于系统具有较好的可扩展性和低侵入性。由于统一接口已经建立，后续若需要引入新的 L2 特化结构，只需在现有抽象下补充实现并接入已有 runner 与 benchmark 即可，无需重写整套实验框架。同时，系统将核心 Rust 实现与外围脚本、结果材料分层组织，尽量减少了对主仓库已有逻辑的直接扰动。

第五个优点在于系统具有明确的平台依托与工程可落地性。由于本文工作直接构建在 `NautilusTrader` 现有框架之上，因此论文中的 baseline、数据模型、benchmark 入口和 replay 运行入口都具有明确的代码锚点，而不是脱离真实工程环境的人造实验平台。这使得本文的系统设计既保留了研究型比较所需的可控性，也兼顾了与实际代码仓库相衔接的可落地性。

当然，这一设计也存在明显局限。首先，当前系统更接近研究型验证平台，而不是完整生产交易平台。它关注的是本地 L2 维护、验证与测量闭环，而不是风控、网络接入、策略编排、分布式部署和持久化恢复等更大范围的系统问题。其次，当前系统的真实工作负载仍以主数据集和核心查询场景为中心，虽然能够支撑论文分析，但在跨市场、跨日期和跨品种扩展方面仍有进一步完善空间。再次，三种特化结构虽然都已纳入统一设计，但其当前实现成熟度并不一致，尤其是 `L2VecBook` 与 `L2GridBook` 仍存在较大的调优空间，因此系统当前更适合作为“设计路线验证平台”，而不是直接将所有特化结构视为已经充分成熟的最终方案。

## 3.5 设计中的制约因素

本系统的第一项制约因素，是必须保持与 baseline 的输入语义和比较口径一致。由于 baseline 被视为 correctness 参考实现，任何特化结构都不能通过修改原始输入解释方式来换取性能优势。这意味着系统在设计时必须优先保证输入一致、顺序一致和查询语义一致，而不能为了追求局部优化随意改变 `delta` 处理规则。

第二项制约因素，是需要在专门化与统一性之间取得平衡。本文的目标虽然是面向 L2_MBP 场景做结构特化，但系统又不能因此完全抛开原有仓库的通用抽象与既有工程边界。若专门化过强，系统可能失去与 baseline 的可比性，也会增加接入成本；若统一性约束过强，则特化结构的优势又难以体现。因此，第三章的总体设计实际上是在“可比性”和“可优化性”之间寻找平衡点。

第三项制约因素，是研究时间、数据规模和实验成本的共同限制。L2 订单簿维护系统不仅需要实现结构本体，还需要构建 correctness harness、benchmark、replay runner 和结果汇总链路。与单一算法实现相比，这类系统工作天然具有较高的调试和验证成本。尤其是在需要多轮重复实验、记录峰值内存和整理结果摘要的情况下，实验组织本身也成为设计必须考虑的约束。

另一个现实制约因素，是本文必须尽量遵守 `NautilusTrader` 现有仓库的模块边界与工程组织方式。由于研究实现并不是独立代码库，而是直接位于既有项目之中，因此新接口、新结构与新 runner 的加入都需要兼顾已有 crate 结构、原生 baseline 语义以及主仓库的可维护性。这一约束使得系统设计不能只追求理论上的最短路径，还需要考虑如何在现有框架中以较低侵入方式落地。

第四项制约因素，是系统边界必须保持适度收敛。若把问题进一步扩展到数据库持久化、复杂 checkpoint、跨节点同步或完整交易平台功能，那么论文的主线就会迅速发散，难以围绕“低延迟交易场景下的本地 L2 订单簿维护”形成清晰贡献。因此，本文在设计上明确将重点限制在原始增量解析、本地状态维护、统一查询、正确性验证和性能测量这几个紧密相关的部分。

最后，还需要考虑不同结构路线自身的工程约束。树结构、向量结构和 grid 结构对应不同的优化方向，它们在动态插删、局部访问和稀疏索引方面各自带来新的实现复杂度。系统总体设计必须容纳这些差异，但又不能让外围 runner 与验证框架被具体实现细节绑死。这也是为何统一接口在本章中被赋予核心地位的原因。

## 3.6 成本与工作量估算

从工程实施角度看，本文系统的工作量主要集中在 baseline 建模、统一接口构建、三种特化结构实现、验证与测量框架构建以及结果整理五个方面。其中，baseline 建模与统一接口构建是后续工作的前提；`L2TreeBook`、`L2VecBook` 与 `L2GridBook` 则代表不同复杂度层级的结构实现；correctness 与 replay/benchmark 框架则是保证实验结论可靠性的必要成本。

为了更直观地说明各部分的实施负担，本文将主要模块的工作量估算整理如表 3-1 所示。

表 3-1 系统主要模块的工作量估算

| 模块名称 | 主要内容 | 实现复杂度 | 测试复杂度 | 调优难度 |
| --- | --- | --- | --- | --- |
| baseline 建模与接口适配 | 分析原生 `OrderBook(BookType::L2_MBP)` 路径，接入统一 `L2BookOps` | 中 | 中 | 中 |
| `L2TreeBook` | 面向 price level 的有序树结构实现与 baseline 对照 | 中 | 中 | 中 |
| `L2VecBook` | 基于连续内存的有序向量结构实现与动态路径处理 | 中 | 高 | 高 |
| `L2GridBook` | 基于 tick 离散化与稀疏页组织的专门化结构实现 | 高 | 高 | 高 |
| correctness 与 replay/benchmark 框架 | 构建统一比较、回放、测量与记录机制 | 中 | 高 | 中 |
| 结果采集与汇总 | 原始结果归档、重复实验统计和摘要输出 | 低 | 中 | 低 |

从表 3-1 可以看出，系统工作量并不只来自订单簿结构本体。尤其是在本文这种以“系统实现 + 实验验证”为主线的研究中，正确性比较、真实 replay 与结果汇总所需的工作，实际占据了相当重要的比例。另一方面，三种特化结构虽然都服务于同一研究目标，但由于设计思路不同，其实现和调优成本并不一致。其中，`L2TreeBook` 与 baseline 的过渡更平滑，工程复杂度相对可控；`L2VecBook` 主要难点在于动态插删路径与连续内存布局之间的平衡；`L2GridBook` 则由于涉及离散化映射、页管理和最佳价缓存等问题，具有更高的实现与调试门槛。

因此，本节的工作量估算进一步说明，本文并不是对几种数据结构做轻量级替换实验，而是在现有仓库基础上搭建了一套包含实现、验证、测量与结果处理的完整本地 L2 维护系统原型。第四章将继续围绕这些模块展开具体实现说明。

## 3.7 本章小结

本章围绕面向低延迟交易场景的本地 L2 订单簿维护系统，完成了从需求分析到总体设计的展开。首先，本文明确了系统在统一输入、状态维护、核心查询、验证测量和研究闭环方面的功能需求，并从低时延、高吞吐、正确性可验证、内存可控、可扩展和可复现等角度说明了非功能需求。随后，本文给出了系统总体架构，指出系统应以原始 `delta` 作为统一输入，以 `L2BookOps` 作为核心抽象边界，在该边界下组织 baseline 与三种特化结构，并通过 replay、benchmark、correctness 和结果汇总形成实验闭环。

在此基础上，本章进一步将系统划分为数据输入与解析、订单簿核心维护、查询与校验、benchmark 与 replay 运行以及结果采集与汇总五个功能模块，并分析了系统总体设计的优势、局限与制约因素。最后，通过工作量估算说明，本文的工作不仅包括若干结构实现，还包括验证与测量框架的完整构建。

综上，第三章完成了从第二章理论基础到第四章具体实现之间的过渡。下一章将在本章总体设计的基础上，进一步介绍统一接口、baseline 集成以及 `L2TreeBook`、`L2VecBook` 和 `L2GridBook` 的具体实现过程。
