# 第一章 绪论

## 1.1 课题背景

限价订单簿是当代电子交易市场的核心组织方式之一。已有研究和相关专著普遍指出，限价订单簿不仅承担买卖撮合的基础功能，同时也是理解市场微观结构、分析流动性分布以及研究交易执行问题的重要状态载体。[Gould et al., 2013; Cartea et al., 2015] 在这一背景下，低延迟交易、量化研究以及历史回放分析，均不再满足于只读取离散快照，而是需要围绕连续到达的市场事件维护可查询、可回放、可验证的本地盘口状态。

从盘口层级看，L1、L2 与 L3 关注的信息粒度并不相同。通常而言，L1 主要描述最优买卖价及其对应数量，L2 描述按价格聚合后的多档市场深度，L3 则进一步保留逐笔订单与队列层级信息。相关数据文档和订单簿回放系统资料也普遍将 Level-1、Level-2 和 Level-3 区分开来，并强调 L2 的核心对象是按价位聚合后的 market depth，而非逐笔订单本身。研究层面上，已有文献表明，最优报价之后的订单簿信息仍然具有增量信息含量，订单流不平衡与短期价格变化之间也存在显著联系，这进一步说明多档簿面状态对于短期交易决策和高频研究具有现实价值。[Cao et al., 2009; Cont et al., 2014; Lucchese et al., 2024]

在实际系统中，交易所原始市场数据通常以消息流或增量事件的形式持续到达，本地系统必须依据这些原始事件顺序维护订单簿状态，而不是每次等待完整快照后再重建簿面。相关技术报告和公开系统资料均表明，订单簿重建本质上是一个持续消费增量、维护状态并支持后续查询与回放的过程。因此，本地订单簿维护首先是一个状态维护问题和系统实现问题，而不是单纯的静态数据存储问题。[Huang and Polak, 2011]

从工程实现角度看，公开系统已经展示了“通用抽象”与“专门化优化”两类思路。一方面，通用订单簿实现往往需要同时覆盖 L1、L2 与 L3 等多种场景，以保证统一语义和接口兼容性；另一方面，面向特定层级、特定工作负载的专门化结构又能够在查询局部性、路径压缩和内存组织方面获得额外收益。这意味着，在纯 `L2_MBP` 场景下，若系统目标被进一步收紧到本地维护、最优价查询、top-N 查询和 replay 支撑，那么在保持语义正确性的前提下，对数据结构与关键路径进行更强的专门化，具有明确的工程研究价值。

基于上述背景，本文将研究对象限定为面向低延迟交易场景的本地 L2 订单簿维护系统，重点关注 `L2_MBP` 场景下按价位聚合后的 price level 维护问题。论文不将重点放在重新设计底层存储引擎或复杂持久化体系上，而是围绕原始 L2 增量 `delta` 数据这一 `source of truth`，讨论如何在本地侧高效完成状态维护、最优价与 top-N 查询、replay 与状态重建，以及 correctness 与性能测量支撑，从而为后续的策略研究和低延迟决策提供稳定的盘口状态基础。

## 1.2 国内外研究现状

从国外研究脉络看，限价订单簿研究已经形成了较为清晰的基础框架。Gould 等的综述系统梳理了限价订单簿的经验事实、建模方法与未解决问题，至今仍是相关研究的重要入口；Cartea 等关于算法交易与高频交易的专著，则从执行、做市、微观结构与高频数据处理等角度，建立了订单簿研究与交易系统问题之间的联系。[Gould et al., 2013; Cartea et al., 2015] 这些工作共同说明，订单簿并非只是交易所内部的撮合容器，而是研究价格形成、流动性分布和执行成本的重要载体。

在市场微观结构层面，国外研究长期关注订单簿的动态建模、信息含量以及价格冲击机理。Cont、Stoikov 与 Talreja 提出的随机订单簿动力学模型，为从连续时间视角分析订单簿事件提供了可估计、可计算的建模基础；Cont、Kukanov 与 Stoikov 进一步指出，短时间尺度上的价格变化与最优买卖盘处的 order flow imbalance 密切相关，其影响强度与市场深度之间存在联系；Cao、Hansch 与 Wang 则表明，最优价后方的簿面信息对价格发现具有增量价值。由此可见，国外研究早已不把订单簿视为单纯的价格列表，而是将其视为流动性、信息与短期价格形成的重要状态空间。[Cont et al., 2010; Cont et al., 2014; Cao et al., 2009]

在订单簿数据重建与研究基准方面，国外已经积累了较成熟的技术路线。LOBSTER 的技术报告明确说明，其系统基于订单处理过程重建历史订单簿，并强调高效数据结构对于大规模数据在线生成的重要性；一些 benchmark dataset 工作则进一步将订单簿数据作为机器学习和预测研究的标准测试对象，以提升不同方法之间的可比性；近期研究也展示了围绕订单簿表征、数据处理管线与高频收益可预测性的系统化趋势。[Huang and Polak, 2011; Ntakaris et al., 2018; Lucchese et al., 2024] 总体来看，国外相关研究已经从“如何重建订单簿”逐步扩展到“如何围绕订单簿建立可复现的研究闭环”。

除学术研究外，工程导向的开源系统也提供了有价值的参考。一些公开交易系统和回放系统围绕 order book reconstruction、market replay、latency 建模以及深度访问等问题给出了实际实现路径。这些项目虽不完全等同于本文的研究对象，但它们说明，围绕订单簿重建、回放和低延迟访问的工程问题，已经成为学术研究之外的重要实践方向。对本文而言，这类工程资料的意义在于提供系统边界、实现组织与工作负载设计的参照。

从国内研究情况看，相关工作更多集中在中国市场的订单簿信息含量、订单流不平衡、事件激励与价格冲击等问题上。已有实证研究考察了高频交易数据下订单流不平衡对股票价格的冲击作用，近年的研究则进一步利用逐单委托数据重建实时演化的限价指令簿，分析状态依赖的 Hawkes 激励效应以及多层级订单流不平衡对价格冲击的解释能力。[王春峰等, 2007; 刘志东、赵致远, 2022; 刘志东、王超, 2023] 由此可见，国内学术研究在利用订单簿解释价格形成与交易行为方面已具有相当积累，但其主要关注点仍偏向市场微观结构实证分析，而不是将“低延迟交易场景下的本地 L2 维护系统”作为独立系统问题进行系统展开。

在国内工程实践中，也存在面向量化交易、行情接入与本地部署的系统平台。公开资料表明，这类系统通常重视低时延处理、交易接口整合以及订单簿相关能力，但其公开定位更多仍偏向通用交易平台建设，而不是专门围绕 `L2_MBP` 本地维护路径开展结构化比较。相较于国际开源系统与国外研究资料，国内公开工程材料在“通用平台能力”方面更加丰富，而在“围绕本地 L2 维护路径进行系统化设计与验证”的论述上仍有进一步整理空间。

进一步看，L1、L2 与 L3 的设计差异也决定了系统优化方向并不相同。面向 L1 的系统更多关注最优报价访问，面向 L3 的系统往往需要保留逐笔订单与队列信息，而面向 L2 的系统则处于两者之间，既需要保持多档 price level 的有序维护，又不必完整保留逐单队列语义。在这种背景下，通用系统与专用系统之间的取舍就显得尤为重要：前者强调统一语义和兼容性，后者强调特定 workload 下的路径压缩、连续内存与访问局部性。基于这一现实，围绕“低延迟交易场景下的本地 L2 订单簿维护系统”展开更具体的系统设计与比较，具有明确的研究意义与工程展开空间。

综上，国内外相关研究已经为订单簿动态建模、信息含量分析、原始消息重建以及 replay 工程实践提供了丰富基础，但现有成果往往分散在市场微观结构、数据重建、机器学习和交易平台实现等不同语境中。相较于这些方向，针对“低延迟交易场景下的本地 L2 订单簿维护系统”这一更具体的问题，仍有进一步系统化梳理和工程验证空间。本文的工作正是在这一问题收束基础上展开：以原始 L2 增量 `delta` 为中心，围绕 baseline 与多种 `L2_MBP` 特化结构，建立统一设计、实现和验证框架。

## 1.3 研究意义、研究内容与研究目标

从研究意义看，本文首先具有明确的工程意义。本地 L2 订单簿维护处于交易所原始增量行情与策略、研究、回放、执行逻辑之间的关键位置。若本地维护路径存在不必要的抽象开销或状态组织不当，就会直接影响最优价访问、top-N 深度查询、簿面特征提取以及 replay 的效率与一致性。因此，围绕 `L2_MBP` 场景收紧问题边界，讨论如何在本地高效维护盘口状态，有助于把“低延迟”从抽象目标转化为可实现、可比较、可验证的系统问题。其次，本文具有方法意义。论文并非孤立比较几种数据结构的局部跑分，而是从系统视角讨论输入处理、状态维护、查询接口、验证链路和测量框架之间的关系，使不同实现能够在相同语义和统一条件下被分析。再次，本文还具有面向交易与研究场景的应用意义。对于低延迟交易，稳定的本地盘口状态是策略状态感知的重要基础；对于量化研究和历史回放，准确的本地重建结果又是特征计算、问题定位和实验复现的重要前提。

从研究内容看，本文首先以原生 `OrderBook(BookType::L2_MBP)` 作为 baseline，对通用订单簿在 `L2_MBP` 场景下的维护路径进行建模，并据此分析其进一步专门化的空间。在此基础上，论文构建统一抽象接口与公共机制，使 baseline 与后续特化结构能够在统一输入语义和相近调用方式下完成接入、维护与查询。这样的处理有助于避免因接口差异而导致的不可比问题，也为后续 correctness 验证与 benchmark 测量提供一致前提。

在具体结构设计上，本文围绕 `L2_MBP` 实现三种特化结构，即 `L2TreeBook`、`L2VecBook` 和 `L2GridBook`。其中，`L2TreeBook` 保留有序结构，同时去除 L2 场景下并不必要的订单级语义，目标是在保持稳定动态更新能力的同时降低通用路径开销；`L2VecBook` 侧重连续内存布局与查询局部性，希望通过更紧凑的 price level 组织改善本地维护效率；`L2GridBook` 则利用 tick 离散化思想进行更激进的结构特化，探索在已知价格粒度约束下是否能够进一步压缩更新与访问路径。需要强调的是，这三条路线都具有明确设计动机，它们并非简单的备选实现，而是针对同一问题从不同结构假设出发的系统化尝试。

除数据结构本体外，论文还包括 correctness 验证、microbench 与 replay workload 设计，以及结果组织与分析支撑等内容。也就是说，本文的研究对象不是单一容器，而是一套完整的本地 L2 订单簿维护系统。系统围绕原始 L2 增量 `delta` 展开，将其作为 `source of truth`，在顺序处理增量的同时维护本地状态，并支持最优价查询、top-N 查询、状态重建与回放分析。通过将实现、验证和测量纳入同一研究框架，论文试图使问题的提出、方案的实现与结论的形成处于一条可追踪的逻辑链上。

从研究目标看，本文主要追求三个层面的目标。第一，在低延迟交易场景下提升本地 L2 订单簿维护效率，使系统能够围绕原始 `delta` 数据完成高效更新与核心查询。第二，在优化效率的同时保持处理语义与状态结果的正确性，确保本地簿面能够作为策略和研究使用的可信状态基础。第三，建立可复现、可扩展的验证框架，使 baseline 与不同 `L2_MBP` 特化结构能够在统一条件下持续比较，并为后续的调优、扩展和系统演进提供实验基础。上述目标共同构成了本文从系统设计、系统实现到测试验证的主线。

## 1.4 论文结构

第一章为绪论。本章介绍课题背景，梳理国内外研究现状，明确论文的研究意义、研究内容与研究目标，并给出全文结构安排。其作用在于将研究问题收紧到“低延迟交易场景下的本地 L2 订单簿维护”，为后续章节搭建统一阅读入口。

第二章为相关技术与理论基础。本章将首先界定 L2 订单簿与本地维护问题的基本概念，进一步说明原生订单簿实现机制与 baseline 所依赖的技术基础，并分析低延迟本地维护涉及的关键技术问题，为后续系统设计提供理论支撑。

第三章为系统需求分析与总体设计。本章从本地 L2 订单簿维护系统的实际目标出发，分析其在输入处理、状态维护、核心查询、验证和测量方面的需求，在此基础上给出系统总体设计、功能模块设计，并讨论设计方案的优劣、制约因素和工作量估算。该章承担由理论基础过渡到系统方案的作用。

第四章为系统实现。本章是全文的核心实现章节，将依次介绍实现基础、统一接口与公共机制、baseline 集成与对照实现，以及 `L2TreeBook`、`L2VecBook`、`L2GridBook` 三种特化结构的实现过程。同时，本章还将给出正确性验证模块、benchmark 与 replay 测量模块，以及结果处理与写作分析支撑部分的实现内容，完整呈现系统落地过程。

第五章为测试与结果分析。本章说明测试环境与测试设计，在统一框架下对 baseline 与不同 L2 特化结构开展正确性和性能验证，并结合 microbench 与 replay workload 对测量结果进行分析。该章体现了“系统设计到系统实现，再到测试验证”的逻辑递进，是评价本文研究目标达成情况的重要章节。

第六章为总结与展望。本章对全文工作进行总结，归纳本文在面向低延迟交易场景的本地 L2 订单簿维护方面所完成的设计、实现与验证工作，并在此基础上讨论当前研究的局限以及后续可能的优化方向。
